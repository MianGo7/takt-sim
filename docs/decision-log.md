# Decision log

Tooling and modelling decisions in the form of architecture decision records
(ADR). Each record states the context, the decision, the alternatives that
were rejected, and the consequences. A decision that changes later is not
edited in place; a new record supersedes it and says so.

---

## ADR-0001: Discrete-event simulation in Python with SimPy

Date: 2026-10-06. Status: accepted.

**Context.** The task asks for a simple simulation model of a part of a smart
factory and for a detailed description of its results. It names FlexSim
Express and the AnyLogic Personal Learning Edition as usable standard
software and explicitly permits alternative tools that are suitable for
manufacturing simulation. The model compares maintenance strategies across
several scenarios, so it has to be run many times with controlled random
numbers, and its results have to be reproducible by a reader.

**Decision.** The model is written in Python with SimPy, a process-based
discrete-event simulation library. Machines, buffers, degradation, and
maintenance policies are ordinary Python code, the experiments are defined
in code as well, and the results are evaluated with the scientific Python
libraries.

**Alternatives.** FlexSim Express was rejected because it is only available
for Windows, whereas the development machine runs macOS. The AnyLogic Personal
Learning Edition runs on macOS and would have provided an animated model with
little effort. It was rejected because the model is assembled in a graphical
editor, which makes a change to the model hard to review in the version
history, and because its rules cannot be covered by automated tests that run
outside the tool. For a comparison of strategies, the ability to script every
experiment and to test every rule outweighs the animation. Writing an event
scheduler from scratch was rejected as well, since it would have reproduced
what the library already provides and would have added a source of errors
without contributing to the question of the project.

**Consequences.** The model has no three-dimensional animation, so its
behaviour has to be made visible through diagrams and result charts. Its
credibility cannot rest on the reputation of a commercial tool and has to be
established through verification against analytic values, which is planned as
backlog item B5. In return, every result in the report can be traced to a
commit, a parameter set, and a seed.

## ADR-0002: Python 3.13, uv, and the scientific Python libraries

Date: 2026-10-06. Status: accepted.

**Context.** The results have to be reproducible on another machine, which
requires the interpreter version and every dependency, including the indirect
ones, to be fixed.

**Decision.** The project targets Python 3.13 and is managed with uv, which
creates the virtual environment and records the exact versions of all
dependencies in `uv.lock`. The runtime dependencies are SimPy for the
simulation, NumPy for the random number generators, SciPy for the confidence
intervals, pandas for the result tables, and Matplotlib for the figures.

**Alternatives.** A `requirements.txt` file installed with pip was rejected
because it does not lock indirect dependencies unless it is generated by a
further tool. Poetry would have met the requirement, but uv additionally
installs the interpreter in the required version, which removes one manual
step from the set up. Plotting with seaborn or Plotly was rejected because
the figures are static, printed in black and white, and few in number, so
that a second plotting layer would be a dependency without a requirement
behind it.

**Consequences.** A reader needs uv and no other tool to repeat the
experiments. Every later change to the dependencies is recorded in this file.

## ADR-0003: Ruff, pytest, and continuous integration

Date: 2026-10-06. Status: accepted.

**Context.** A simulation model produces plausible looking numbers even when
it is wrong, so errors have to be caught by checks that do not depend on a
person reading the output.

**Decision.** The code style and the static checks are enforced with Ruff, the
tests are written with pytest, and both run on every push through a GitHub
Actions workflow. The rule set includes the NumPy rules, which reject the
legacy global random state and thereby support the reproducibility
requirement NFR1.

**Alternatives.** The combination of Black, isort, and Flake8 was rejected
because Ruff covers all three with one configuration. The `unittest` module of
the standard library was rejected because parametrised tests, which the
verification against analytic values relies on, are considerably shorter in
pytest.

**Consequences.** A change that breaks a rule of the model or the code style
is visible before it reaches the main branch.

## ADR-0004: Diagrams as PlantUML sources

Date: 2026-10-06. Status: accepted.

**Context.** The report needs diagrams of the modelled process and of the
structure of the model, and these have to stay consistent with the code.

**Decision.** The diagrams are written as PlantUML sources in
`docs/diagrams/` with a shared style file, and they are rendered to vector
graphics for the report.

**Alternatives.** A graphical editor such as draw.io was rejected because its
files cannot be compared meaningfully between two versions, so a diagram that
no longer matches the code would go unnoticed.

**Consequences.** A change to a diagram appears in the history next to the
code change that caused it. PlantUML and Graphviz have to be installed to
render the figures.

## ADR-0005: A published simulation study as the reference case

Date: 2026-10-06. Status: accepted.

**Context.** The task asks for a model that relates to an organisation the
author knows or to a case study based on the literature. A simulation model is
only as credible as its parameters, and a comparison of maintenance policies
needs cycle times, buffer capacities, degradation behaviour, and repair times
that do not stem from the modeller's own preference.

**Decision.** The reference case is the serial configuration C1 of Dadfarnia
et al. (2023), a line of six milling machines with five buffers. Every
parameter that the paper states is adopted unchanged, and every point it
leaves open is listed as an assumption in `concept.md`.

**Alternatives.** Data from a company known to the author were rejected
because no manufacturing company with accessible failure and repair records
was available, and estimated values would have been presented with an
authority they do not have. A generic line with freely chosen parameters was
rejected because its results could not be compared with anything. Among the
published cases, this one was chosen over studies of serial lines without
condition monitoring because it covers the question of the project directly,
documents its parameters completely enough to be rebuilt, and publishes
results per policy that an independent implementation can be validated
against.

**Consequences.** The model can be validated against published values, which
a self defined case would not allow. The case is fictional by the statement of
its authors, so the results describe a documented model line and not a real
plant. An empirical study of failure and repair times in an industrial plant
is consulted in B5 to check the order of magnitude of the parameters. The paper leaves
several details open, so an exact reproduction of every published value is not
to be expected, and each deviation has to be examined in B5.

## ADR-0006: One configuration, two policies, and an abstract signal quality

Date: 2026-10-06. Status: accepted.

**Context.** The reference case comprises five configurations and five
maintenance policies, two of which infer the machine health from the quality
of finished parts with dedicated algorithms. The report is limited to ten
pages of text.

**Decision.** The model covers the serial configuration and two policies,
run-to-failure and condition-based maintenance with direct sensing. Instead of
the two inferring algorithms, the quality of the signal is modelled through
two error rates: the probability that a reading at or below the alarm
threshold raises an alarm, and the probability that a reading above it raises
a false alarm. The alarm threshold, the two error rates, and the buffer
capacity are varied systematically. The periodic inspection policy and the
configurations with parallel machines are specified as FR14 and FR15 and
deferred.

**Alternatives.** Rebuilding all twenty-five scenarios of the paper was
rejected because it would have turned the project into a replication without
a question of its own, and because the two algorithms are documented in a
separate publication and not in the paper. Modelling a sensor with continuous
measurement noise was rejected because the health indicator of the reference
case is discrete, so that noise would require a further assumption about how a
noisy value maps to an alarm, whereas two error rates correspond directly to
the true positive rate and the false positive rate with which the paper itself
evaluates a monitoring system.

**Consequences.** The paper reports the perfect monitoring system only at the
setting that maximises quality. The variation of the threshold therefore goes
beyond the published results, and its outcome cannot be validated against
them. The validation rests on the run-to-failure policy.

## ADR-0007: Hours as the time unit and machine as the term

Date: 2026-10-06. Status: accepted.

**Context.** The reference case states every duration in hours and speaks of
machines, buffers, a source, a sink, parts, and maintainers.

**Decision.** Simulation time is measured in hours, and the model uses the
terms of the reference case.

**Alternatives.** Minutes as the time unit were rejected because every
parameter would have to be converted, which invites errors without adding
precision. The term station was rejected because a reader who compares the
model with the paper should find the same words in both.

**Consequences.** Parameters can be checked against the paper without
conversion.

## ADR-0008: The run covers the half-open interval from 0 up to the run length

Date: 2026-10-06. Status: accepted.

**Context.** In a line with constant cycle times, a part can reach the sink at
exactly the end of the run. The reference case counts only parts that have
left the line by the end of the run (p. 416) and does not say how an arrival
at that instant is treated. For the reference line over 10,080 hours the
choice changes the output by one part.

**Decision.** A run covers the half-open interval from 0 up to but excluding
the run length, and a part that arrives at the sink at exactly the run length
is not counted. This is the behaviour of `env.run(until=...)` in SimPy, which
stops before the events of the stop time are processed, so that the model
needs no special rule. The first part leaves the reference line at 6 hours,
and the output of S0 over 10,080 hours is therefore 10,074 parts.

**Alternatives.** Counting an arrival at exactly the run length was rejected
because it would require running past the stop time or a correction after the
run, and it would depart from the default of the simulation library without a
reason that the reference case supplies.

**Consequences.** The expected output of S0 is `run length - 6` parts for an
integer run length of at least 6 hours, and the tests compare with equality.

## ADR-0009: Single modules and one random number stream per machine from the start

Date: 2026-10-06. Status: accepted.

**Context.** B2 introduces the configuration and the model. The model has no
random element yet, because the cycle times are constant (A3) and the
degradation follows in B3.

**Decision.** `config.py` and `model.py` are single modules, as in the
architecture of the package. A sub-package for the model is introduced only
if the module grows beyond what is readable, and that step is then recorded
in its own ADR. The root seed of a run is part of the run configuration, and
one generator per machine is derived from it with `SeedSequence.spawn` and
handed to the machine, although the machine does not draw from it before B3.
The derivation currently sits in `model.py` next to the line it feeds and
moves into the experiment runner in B4, which owns replications.

**Alternatives.** Adding the seed and the streams in B3 was rejected because
the construction of a machine and the signature of the run would change
together with the first draw, which would mix an interface change with a new
rule. A single shared generator was rejected because a draw made by one
machine would shift the sequence of every other machine, which defeats common
random numbers across scenarios.

**Consequences.** The test that two runs with the same seed are identical
holds trivially in B2 and becomes informative in B3, when the degradation
draws from the streams. In B3 each machine will need several streams, one per
source of randomness, so the list of generators becomes one record per
machine.

## ADR-0010: Failure by interruption, health as a step count, and streams per machine and source

Date: 2026-10-06. Status: accepted.

**Context.** B3 adds the degradation, the failure, and the corrective repair.
Three points are open. A failure has to stop a machine that is waiting for a
part or processing one, the health has to be exact, and the random number
streams have to stay independent when a source of randomness is added. The
reference case scraps the part in process at a failure (p. 417) and is
silent on a machine that is starved or blocked at that moment.

**Decision.** The health is stored as the integer number of remaining steps
and exposed as that number divided by eight, which is exact. A second process
per machine draws the Weibull intervals, lowers the health, and on reaching
zero sets the failed flag and requests a maintainer through a first in, first
out SimPy resource with the number of maintainers as its capacity (A8). The
process of the machine is interrupted when it is waiting for a part or
processing one. A part held at that moment is scrapped, and a withdrawn wait
takes no part. A machine that is blocked is not interrupted: its finished part
is handed over first, and the machine then waits for the repair (A9). A part
that a buffer hands over at the very instant of the failure belongs to the
machine and is scrapped, so that no part disappears without a count. The
degradation continues in clock time while the machine is starved or blocked
(A2) and stops while it is failed. The streams are one record per machine
with one generator per source of randomness. Each machine receives a child of
the root `SeedSequence` by its position, and its sources are children of that
child, so that the stream of a machine depends on the seed and the position
only. B6 adds the generator for the sensor errors to the record.

**Alternatives.** Storing the health as a float and subtracting the step was
rejected because the exactness then rests on the step being a power of two,
which the integer makes independent of the value. Checking the failed flag at
the start of every cycle instead of interrupting was rejected because a
machine would continue a cycle and release a part after it had failed, and a
starved machine would take a part during its repair. Scrapping the finished
part of a blocked machine was rejected because the part has left the
processing step, and scrapping it would add a loss that the reference case
does not describe. Spawning the streams of all machines from one parent
without the second level was rejected because the next source of randomness
would then shift the streams of the following machines.

**Consequences.** The throughput of S1 depends on A9 whenever a machine fails
while it is blocked, and B5 examines this together with A1 to A8. A tie
between a failure and a handover is resolved in favour of the failure, which
has probability zero for continuous Weibull intervals and is tested only by
its construction. The policy interface of the architecture is introduced in
B6, when there is a second policy to exchange, and the corrective repair is
until then part of the maintainers.
